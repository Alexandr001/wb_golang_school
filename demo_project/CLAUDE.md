# CLAUDE.md

Учебный микросервис (WB Go School): заказы приходят из Kafka → валидируются → сохраняются в PostgreSQL → кэшируются в памяти → отдаются по HTTP и простой web-странице. Всё поднимается через `docker compose up`.

Первоисточники: [`tz.md`](tz.md) — задание, [`PLAN.md`](PLAN.md) — план реализации с обоснованием стека. При расхождении этого файла с ними — правда в них, а CLAUDE.md нужно обновить.

## Команды

```bash
make up             # поднять окружение целиком (postgres + kafka + сервис)
make logs           # логи сервиса
make down           # остановить, данные сохранить
make reset          # остановить и стереть тома (обязательно после правки db/init)
make psql           # psql под пользователем приложения

make build          # сборка в ./bin (CGO_ENABLED=0)
make run            # локальный запуск (нужен .env: cp .env.example .env)
make fmt vet lint   # обязательный минимум перед сдачей изменений
make tidy           # go mod tidy
make help           # все цели
```

`make lint` сам доставит `golangci-lint` v2.12.2 в `$GOPATH/bin`, если его нет. Конфиг линтера — `.golangci.yml` (**формат v2**: `linters.settings`, отдельная секция `formatters`; синтаксис v1 не подойдёт).

## Стек

Go 1.26 · stdlib `net/http` (роутер 1.22+, без фреймворка) · `pgx/v5` + pgxpool · `segmentio/kafka-go` · `goose/v3` + `embed.FS` · `go-playground/validator/v10` · `caarlos0/env/v11` · `log/slog` · PostgreSQL 17 · Kafka 4.1.2 (KRaft).

Обоснование каждого выбора и отвергнутые альтернативы — в разделе 1 `PLAN.md`. **Не добавляй зависимости без нужды**: ORM, роутер, Viper, zap сознательно не используются.

## Архитектура

```
Kafka (topic: orders)                         HTTP :8081
   │ FetchMessage                                 │ GET /order/{uid}
   ▼                                              ▼
broker/kafka.Consumer                    transport/http.Handler
   │  unmarshal + validate                        │
   └──────────────► service.OrderService ◄────────┘
                      │           │
                      ▼           ▼
        repository/postgres   cache (LRU)
              (pgxpool)        in-memory
```

Слои и правило зависимостей (внутрь, наружу — никогда):

- `internal/domain` — модели и доменные ошибки. **Ничего не знает** про Kafka, HTTP, SQL. Никаких импортов инфраструктуры.
- `internal/service` — оркестрация: `Save` (репозиторий в транзакции + кэш), `Get` (кэш → БД → кэш). Зависит от интерфейсов, не от реализаций.
- `internal/repository/postgres`, `internal/cache`, `internal/broker/kafka`, `internal/transport/http` — инфраструктура, реализует интерфейсы, объявленные в `service`.
- `cmd/orders-service` — composition root: единственное место, где создаются конкретные реализации и сшиваются между собой.

Порядок старта строго такой: миграции → пул БД → **прогрев кэша** → HTTP-сервер и consumer. Иначе `/readyz` отдаст `200` с холодным кэшем.

HTTP-слой (`internal/transport/http`): `server.go` (таймауты + graceful shutdown), `router.go` (маршруты + `//go:embed static`), `handler.go`, `middleware.go`, `response.go`. Маршруты: `GET /order/{order_uid}` (200 + `X-Cache: HIT|MISS`, 404, 400), `GET /healthz`, `GET /readyz`, `GET /` — страница из `static/`.

## Ключевые инварианты

Их нельзя нарушать «для простоты» — на них держатся требования ТЗ про сохранность данных:

1. **Оффсет коммитится только после успешного `COMMIT` в БД.** `FetchMessage` → обработка → `CommitMessages`. Это at-least-once: при падении сообщение перечитается.
2. **Запись идемпотентна.** `INSERT ... ON CONFLICT (order_uid) DO UPDATE` для `orders`/`deliveries`/`payments`, для `items` — `DELETE` + batch insert. Всё в одной транзакции. Повторная доставка не плодит дублей.
3. **Ошибки делятся на два класса** (`domain.IsPermanent`, `domain.Permanent`):
   - *permanent* (битый JSON, провал валидации) → `warn` в лог с контекстом (topic/partition/offset) + **коммит оффсета**, иначе consumer вечно жуёт «ядовитое» сообщение;
   - *transient* (БД недоступна, таймаут) → backoff-ретраи, при исчерпании **оффсет не коммитим**.
   - Умолчание — transient: неизвестную ошибку безопаснее повторить, чем потерять сообщение.
   - **Валидация не слабее CHECK'ов в БД.** Если правило есть в схеме (`amount >= 0`, `price >= 0`), оно обязано быть и в `validate`-теге: иначе битые данные пройдут валидацию, упрутся в constraint, будут приняты за transient — и consumer уйдёт в вечный ретрай.
   - **Типы модели повторяют типы схемы**: где `INTEGER` — там `int32`, а не `int` (`sm_id`, `sale`, `status`). Переполнение иначе всплывает при кодировании параметра внутри pgx, ещё до отправки на сервер: такая ошибка приходит **без SQLSTATE**, `classifyError` её не опознает, и consumer встаёт намертво. С `int32` её ловит `json.Unmarshal` на входе.
   - Если transient-ошибка не ушла за `KAFKA_MAX_ATTEMPTS`, consumer **останавливает сервис** с ошибкой в логе. Оффсет не закоммичен → сообщение перечитается после перезапуска. Пропускать нельзя: `kafka-go` уже сдвинул чтение, и коммит следующего сообщения неявно закоммитил бы это.
4. **Кэш заполняется только после успешной записи в БД** — иначе отдадим клиенту заказ, которого в базе нет.
   - **Заказ в кэше неизменяем.** `Get` отдаёт указатель на тот же объект, копия не делается: мутация возвращённого заказа молча испортит данные всем читателям.
   - Кэш под обычным `sync.Mutex`, не `RWMutex`: в LRU каждое чтение переставляет запись в начало списка, то есть меняет структуру — под `RLock` это делать нельзя.
   - Прогрев кладёт заказы **от старых к свежим**: последний `Set` самый «свежий» в LRU, поэтому при `CACHE_WARMUP_LIMIT > CACHE_CAPACITY` вытесняются старые, а не актуальные.
   - **Путь чтения пишет в кэш только через `SetIfAbsent`.** Пока запрос ходил в БД, consumer мог положить туда более свежую версию заказа; `Set` затёр бы её устаревшей копией, и кэш протух бы до следующего обновления. `Set` — только для пути записи, где наша версия заведомо свежайшая.
5. **Секреты не логируются.** Всё, что содержит пароль, реализует `slog.LogValuer` с `[REDACTED]` (см. `config.Postgres.LogValue`).
6. **Наружу не течёт ничего, кроме статуса и текста ошибки.** Клиент получает `{"error":"..."}` с общей формулировкой, подробности (SQL, стек паники) — только в лог. Ошибка сериализуется в буфер и лишь потом пишется в сеть: иначе сбой на середине объекта оставит клиенту `200` и обрезанный JSON.
   - Порядок middleware снаружи внутрь: **request-id → access-лог → recover → таймаут**. Лог снаружи recover'а и таймаута — иначе упавшие и подвисшие запросы, ради которых лог и читают, в него не попадут.
   - Чужой `X-Request-Id` принимается только после проверки (≤64 символа, `[A-Za-z0-9._-]`): значение уходит в лог, а непроверенный ввод там ломает разбор.
   - `/healthz` не ходит в зависимости: упавшая БД — не повод перезапускать исправный процесс. Проверки живости логируются на `debug`, иначе healthcheck'и compose забьют лог целиком.
   - **Ушедший клиент пишется в лог как `499`, а не как реальный код.** При обрыве соединения `http.TimeoutHandler` всё равно вызывает `WriteHeader(503)`, и access-лог сообщал бы об ошибке сервера там, где сервер ни при чём. Свой таймаут обработчика отличим: он отменяет производный context, а `r.Context()` принадлежит соединению.
   - `/readyz` проверяет только ping БД. Прогрев кэша не проверяется намеренно: он выполняется до старта сервера, а пустой кэш на пустой базе — законное состояние, и `503` на него не дал бы подняться на чистом окружении.

## Схема БД

`orders` (PK `order_uid`) ← `deliveries` (1:1) · `payments` (1:1) · `items` (1:N), у детей `ON DELETE CASCADE`. Полный DDL — раздел 3 `PLAN.md`.

- Имена колонок один-в-один с JSON-моделью из ТЗ. `transaction`, `name`, `status`, `size` в PostgreSQL 17 не зарезервированы — кавычить не нужно.
- `payment_dt` — `BIGINT` (unix-секунды, как в модели), `date_created` — `TIMESTAMPTZ` (по нему индекс для прогрева кэша).
- Денежные поля целые (`BIGINT`), `NUMERIC` не нужен.
- Приложение ходит под непривилегированным `orders_app`, не под суперюзером (`db/init/01-app-user.sh`). Init-скрипты БД выполняются **только на пустом томе** — после их правки нужен `make reset`.
- Healthcheck БД проверяет **TCP** (`pg_isready -h 127.0.0.1`), а не unix-сокет: пока идут init-скрипты, entrypoint держит временный сервер без TCP-листенера, и проверка через сокет сказала бы «готов» ещё до создания роли приложения.
- **`date_created` после чтения из БД приводится к UTC** (`scanOrder`). pgx декодирует `timestamptz` бинарно, через `time.Unix`, то есть в локальной зоне процесса — параметр сессии `timezone` на это не влияет. Без нормализации JSON заказа зависел бы от таймзоны машины и разошёлся бы с исходным сообщением.

## Конвенции кода

**Ошибки**
- Оборачивать с контекстом: `fmt.Errorf("save order %s: %w", uid, err)`. Проверять через `errors.Is`/`errors.As`, не сравнением строк.
- Sentinel-ошибки живут в `internal/domain/errors.go` (`ErrNotFound`, `ErrInvalidMessage`).
- Текст ошибки — английский, с маленькой буквы, без точки и без «failed to».
- Никогда не глотать ошибку молча. `_ = err` только с комментарием, почему это осознанно.

**Context**
- Первым параметром, имя `ctx`. Не хранить в полях структур.
- Любой поход в сеть/БД — только с `ctx`. `context.Background()` допустим лишь в `main`.

**Интерфейсы и DI**
- Интерфейс объявляет **потребитель** (`service`), а не реализация. Держать их маленькими (1–3 метода).
- Принимать интерфейсы, возвращать конкретные типы. Зависимости — через параметры конструктора `New...`, без глобалов и `init()`.

**Логи**
- Только `log/slog`, структурно: `log.Info("order saved", slog.String("order_uid", uid))`. Никаких `fmt.Printf`/`log.Println`.
- Сообщения на английском, в нижнем регистре; комментарии в коде — на русском.
- Логгер передаётся явно через зависимости; `slog.SetDefault` вызывается один раз в `main`.

**SQL**
- Только параметризованные запросы (`$1`), никакой конкатенации и `fmt.Sprintf` в SQL.
- Явно перечислять колонки, без `SELECT *`.
- Транзакции — через `pgx.BeginFunc`: rollback при ошибке и панике делается за тебя.
- `defer rows.Close()` сразу после получения `rows`, проверять `rows.Err()`.

**Общее**
- Всё, кроме `cmd/`, живёт в `internal/`. Пакеты называются коротко и по смыслу; никаких `utils`, `common`, `helpers`.
- Ранний возврат вместо вложенных `if`. Не плодить абстракции «на будущее».
- Всё настраиваемое — через env в `internal/config`, дефолты пригодны для локального запуска. Новую переменную добавлять сразу в `.env.example` и в `docker-compose.yml`.
- HTTP-сервер всегда с явными таймаутами; `http.Server{}` без них уязвим к slowloris.
- `main()` — только вызов `run() error`: при `os.Exit` не отрабатывают `defer`.
- Перед завершением задачи: `make fmt vet lint` должны быть зелёными.

## Вне скоупа

Сознательно не делаем (решено на старте, не «забыли»): автотесты, DLQ-топик, Prometheus/Grafana, `POST /order`, CI. Архитектура их не блокирует — добавляются поверх существующих интерфейсов. Не добавляй их без явной просьбы.

## Ограничения

- Не коммитить и не пушить без явной просьбы.
- Порт HTTP — `8081`, зафиксирован в ТЗ.
- Формат сообщения Kafka: 1 сообщение = 1 заказ, `value` — голый JSON по модели из ТЗ, `key` = `order_uid`.
- `kafka-init` при старте не только создаёт топик, но и публикует туда `testdata/model.json` — после `make up` в сервисе сразу есть заказ `b563feb7b2b84b6test`. Файл монтируется в контейнер, поэтому эталон модели и демо-данные — это буквально один файл.
